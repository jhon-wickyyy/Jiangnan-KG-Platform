## 5. 图谱模式（Schema Patterns）

`(起点标签)-[:关系]->(终点标签)` 的完整枚举（按数量降序）：

| 模式 | 数量 | 说明 |
|---|---|---|
| `(建筑)-[:属于]->(园林)` | 14 | 全部 14 个建筑挂到园林根节点 |
| `(建筑)-[:相邻]->(建筑)` | 14 | 建筑环线（14 条带环线序号的有向边） |
| `(建筑)-[:相邻]->(花木)` | 8 | 建筑与植物相邻 |
| `(花木)-[:属于]->(园林)` | 8 | 全部 8 个植物挂到园林 |
| `(花木)-[:相邻]->(建筑)` | 8 | 反向相邻边 |
| `(建筑)-[:相接]->(山石)` | 5 | 建筑与山石接触 |
| `(山石)-[:相接]->(建筑)` | 5 | 反向接触边 |
| `(山石)-[:属于]->(园林)` | 3 | 全部 3 处山石挂到园林 |
| `(池沼)-[:属于]->(园林)` | 3 | 全部 3 处水体挂到园林 |
| `(建筑)-[:相邻]->(池沼)` | 2 | 建筑临水相邻 |
| `(建筑)-[:相接]->(池沼)` | 2 | 建筑临水相接 |
| `(池沼)-[:相邻]->(建筑)` | 2 | 反向相邻边 |
| `(池沼)-[:相接]->(建筑)` | 2 | 反向接触边 |

**规律**：
- `属于` 仅单向：要素 → `园林`，共 28 条 = 14+8+3+3（全部业务要素各有一条）。
- `相邻`、`相接` 为对称关系，以两条反向有向边存储（34 = 2×17、14 = 2×7）。
- 不存在 山石↔池沼、花木↔池沼、花木↔山石 之间的直接关系；跨类空间联系都经由 `建筑`。

## 10. 关键观察与平台设计提示

1. **多库一园**：每个园林是 Neo4j 服务器上的一个独立数据库（当前仅 `canglangting` 有数据，`neo4j` 默认库为空）。平台必须支持"数据库选择/切换"，或在上层统一路由。
2. **双坐标系冗余**：`x/y`（笛卡尔）与 `极径_m/极角_度`（极坐标）并存且等价，可互相换算——前端地图渲染可任选其一，`建筑0-1`（大门）恒为原点 (0,0)。
3. **对称关系双写**：`相邻`、`相接` 以两条反向有向边存储；统计"无向相邻对数"需除以 2。`属于` 为单向边。
4. **环线结构**：`相邻.相邻类型 = 建筑环线` 的 14 条边带 `环线序号`（1–14），构成建筑游览环线；这是路径规划/游线推荐功能的核心数据。
5. **属性语义层次**：`相邻类型`（建筑环线/可看/对景）、`中介`（园路/水面/山径…）、`接触类型`（临水/在山上/在山边）提供了丰富的空间语义，可用于可视化图例与空间关系问答。
6. **编号规则**：`{标签}{序号}-{子序号}`，序号疑似对应原始园林测绘图的要素分组（如 `建筑5-*` 为一组）。
7. **数据量小**：单园 29 节点 / 76 边，即使 22 园全部加载，总量仍属小规模图谱，前端可全量加载渲染，无需分页或复杂图算法优化。
8. **Bloom 元数据**：`_Bloom_*` 标签仅存在于 `neo4j` 默认库（空），`canglangting` 库内无，不影响业务查询。
